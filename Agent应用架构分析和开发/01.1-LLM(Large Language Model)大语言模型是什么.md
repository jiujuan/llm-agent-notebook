# 一、LLM 是什么

LLM，全称是 Large Language Model，中文是：大语言模型。

要理解 AI Agent, 必须先理解它的"心脏"——大语言模型(Large Language Model,以下简称 LLM)。

但这节不是技术介绍。我们不深入 Transformer 架构,也不讨论训练细节。我们要做的是:

> 为非 AI 背景的架构师和工程师以及其他人, 建立对 LLM 的正确认知模型。


## 1.1：LLM 到底在做什么

如果你让一个资深 AI 工程师用一句话解释 LLM, 他会说:

**"给定一段文字, 预测下一个最可能出现的文字（token）。"**

就这么简单。

人输入: "今天天气真"
LLM 输出: "好"(概率 35%) / "不错"(概率 22%) / "晴朗"(概率 8%) / ...

**它不做“理解”, 它做预测。**

但当你把这句话放大到数千亿参数、训练数据覆盖人类几乎所有公开文本、模型规模突破某个临界点后,奇迹发生了:

- 它学会了语法, 因为语法让预测更准
- 它学会了事实, 因为事实让预测更准
- 它学会了推理, 因为推理模式让预测更准
- 它学会了写代码, 因为代码模式让预测更准
- 它学会了"听懂"人话, 因为"听懂"让预测更准

**"理解"不是被设计出来的, 是更准的预测的副产品。**

这一点至关重要——它决定了 LLM 能做什么、不能做什么, 以及我们在它之上能做什么。


## 1.2：2个让非技术人员看懂的类比

我们用 2 个类比建立对 LLM 理解的直觉。

### 类比一: LLM 是博学但无手无脚的天才

想象一个读过人类所有书籍、记忆力惊人、能用二十种语言写作的人。他博学到能和你讨论任何话题、能写诗、能写代码、能推演数学题。

**但他被困在一个没有窗户的房间里:**
- 他看不到真实世界
- 他碰不到键盘和鼠标
- 他不知道"今天几号"
- 他不知道"你刚才说了什么"(对话结束就忘)
- 他不知道"我答得对不对"

**这就是原始的 LLM**。一个被困在上下文窗口里的语言天才。

Agent 是什么？**给这个天才装上手脚、眼睛、记忆。** 让他能查数据库、能执行命令、能搜索网页、能记住你上个月说过的话。

### 类比二: LLM 是新时代的"CPU"

| 维度     | 传统 CPU    | LLM             |
| -------- | ----------- | --------------- |
| 角色     | 计算核心    | 推理核心        |
| 输入     | 二进制指令  | 自然语言/Prompt |
| 输出     | 确定性结果  | 概率性结果      |
| 速度     | 纳秒级      | 秒级            |
| 能力来源 | 硬件设计    | 训练数据 + 规模 |
| 编程方式 | 指令集/语言 | Prompt/微调     |

CPU 不能直接面对用户, 需要操作系统、应用软件。同样,  LLM 也不能直接面对用户, 需要 Agent 这种"操作系统层"来调度它的能力、约束它的行为、连接它的输入输出。


## 1.3：LLM 已经能做什么——能力全景图(2024-2026)

截至 2026 年,主流大模型已经具备的能力(注意, 不是所有模型都具备全部能力):

**语言能力**
- 多语言理解与生成(覆盖 100+ 语言)
- 风格迁移(学术、口语、营销、技术)
- 长文本生成(数千到数万字保持连贯)
- 文本改写、扩写、缩写、摘要

**推理能力**
- 数学推理(基础到中等竞赛级别)
- 逻辑推理(演绎、归纳、类比)
- 多步规划
- 因果推断(在一定范围内)

**代码能力**
- 代码生成、补全、重构
- 跨语言翻译(如 Python 转 Rust)
- Bug 定位与修复建议
- 测试用例生成

**知识与记忆**
- 通用知识(覆盖到训练截止日期)
- 领域知识(医学、法律、编程等)
- 实体关系(但可能"知道"也可能"编造")

**多模态能力(部分模型)**
- 图像理解与描述
- 文档解析(图表、表格、公式)
- 音频转写
- 视频理解(部分模型)

**对话与角色能力**
- 长期对话(在上下文窗口内)
- 角色扮演与风格控制
- 意图识别
- 情感识别

**工具能力(原生支持的模型)**
- Function Calling(结构化输出)
- JSON / 工具 Schema 解析
- 多步工具规划


## 1.4：LLM 不是万能的—它的边界在哪里

讲 LLM 能力容易让人产生幻觉: "LLM 这么强, 还需要 Agent 干嘛?"

答案是: LLM 的能力不等于 LLM 的可用性。

LLM 像一个博学的咨询顾问, 他能给你答案, 但他不会自己去查数据库、不会去执行命令、不会在出错时反思自己、不会在长任务中保持目标不漂移。

这就是为什么"裸 LLM 调用" 很快遇到天花板, 也是为什么 Agent 这种 LLM 操作系统成为必然。

但在我们进入 Agent 之前,必须先清楚 **LLM 自己有哪些根本性局限**——这是下一节的内容。


## 1.5：LLM 认知模型速查表

在进入下一节前, 留给你一张 LLM 认知模型速查表, 遇到任何 LLM 相关决策时可以回来对照:

```
┌─────────────────────────────────────────────┐
│  LLM 认知模型速查                            │
├─────────────────────────────────────────────┤
│  • LLM 是预测器,不是推理器(虽然看起来像)    │
│  • LLM 是天才,但无手无脚                    │
│  • LLM 一次会话 = 一次独立思考               │
│  • LLM 输出是分布,不是定值                  │
│  • LLM 不会"知道"它不知道什么              │
│  • LLM 没有真实记忆(上下文外全忘)           │
│  • LLM 的"知识"有时效性                     │
│  • LLM 越强 ≠ 越贵,需要按任务分级          │
└─────────────────────────────────────────────┘
```

记住这张卡片,后面所有 Agent 架构决策,本质上都是在为这些局限"打补丁"。

---

> **本节小结**:LLM 是一种新的计算介质——它通过海量数据训练获得通用智能, 但它的"智能"是封闭的、短暂的、概率性的。理解这一点,是理解 Agent 为什么必须存在的起点。


# 二、LLM 的局限性—为什么必须有 Agent

> *"知道 LLM 能做什么很重要,知道它不能做什么更重要——因为所有的工程架构,都是围绕'不能'展开的。"*

上一节我们建立了 LLM 的认知模型: 它是一个被困在房间里的天才,会说话但不会干活。

这一节,我们把这个天才的"牢笼"具体拆开, 逐项说明每条局限是什么, 以及 Agent 怎么把它们一条条打碎。

这九大局限,既是 LLM 的边界,也是 Agent 的设计纲要。


## 2.1：九条局限: LLM 的根本性局限

### 局限 1: 幻觉—它会一本正经地胡说八道

**表现**

LLM 不会说我不知道。当它不知道答案时,它会编造一个看起来很合理但完全错误的答案。

```
User: 介绍一下清华大学 2030 年的新校区
LLM: 清华大学 2030 年新校区位于...(看起来很详细,但完全虚构)
```

**为什么会这样?**

因为 LLM 是预测下一个 token, 而不是检索事实。它没有"真"和"假"的内建概念, 只有哪个 token 序列看起来更合理。

**严重性**

在创意场景(写小说、头脑风暴)里, 幻觉是 feature。
在严肃场景(医疗、法律、金融)里, 幻觉是灾难。

**Agent 怎么解**

- RAG(检索增强生成): 让 LLM 基于真实文档回答, 而不是自由发挥
- 工具调用验证: 关键事实让 LLM 调用 API 查询, 而不是自己编
- 引用溯源: 每个回答必须标注来源, 让用户验证
- 多模型交叉验证: 用不同模型互相校对
- 不确定性表达: 训练/提示 LLM 在不确定时主动说我不确定



### 局限 2: 知识截止—它活在过去的某一天为止

**表现**

LLM 的知识停留在训练数据的截止日期。对截止日期之后发生的事, 它一无所知。

```
GPT-4(2023 年 4 月截止):"2024 年奥运会还没举办"
Claude 3(2024 年 8 月截止):不知道 2025 年 1 月发布的某个 Python 库
```

**为什么会这样?**

训练一次 LLM 的成本是数百万到数千万美元、几周时间。没有人能每天重新训练它。

**严重性**

- 新闻、股价、赛事:完全不可用
- 技术文档:可能落后 1-2 个版本
- 历史事实:基本准确但有边界

**Agent 怎么解**

- 实时搜索工具: 让 LLM 在需要时调用搜索 API
- 知识库外挂: 把最新文档作为 RAG 源
- 时间感知 Prompt: 在 prompt 中显式标注今天是 2026-09-11


### 局限 3: 无手无脚—它触碰不到真实世界

**表现**

原始 LLM 不能:
- 查询数据库
- 发送邮件
- 执行代码
- 操作文件系统
- 调任何业务系统 API

它只能根据训练的数据预测下一个 Token。

**为什么会这样?**

LLM 是一种语言模型, 它的输入和输出都是文本。它没有内置的执行通道。

**严重性**

这是最大的局限——没有工具调用能力的 LLM, 只能是个聊天玩具, 不能做任何实际工作。

**Agent 怎么解**

这就是 Function Calling / Tool Use 机制的诞生原因。让 LLM 输出结构化的"我希望调用某个工具、参数是什么", 然后由 Agent 框架执行这个调用, 把结果返回给 LLM。

```
LLM 思考:用户让我发邮件
LLM 输出:{ "tool": "send_email", "args": { "to": "...", "subject": "...", "body": "..." } }
Agent 执行:真正调用邮件 API
工具返回:{ "status": "ok", "message_id": "..." }
LLM 继续思考:邮件已发送,告诉用户
```



### 局限 4: 无状态—对话结束, 记忆清零

**表现**

你今天和一个 LLM 聊了 3 小时, 讨论了你的职业、你的偏好、你的项目背景。明天你再来, 它完全不记得你。

**为什么会这样?**

LLM 本身没有持久存储。每次推理都是独立的——给定完整上下文(对话历史), 预测下一个 token。对话历史不传过去, LLM 就一无所知。

**严重性**

- 个性化体验: 不可能。LLM 不知道你是谁。
- 长期任务: 不可能。任务跨度超过一次对话就丢失。
- 用户粘性: 不可能。用户每次都要重新介绍自己。

**Agent 怎么解**

- 短期记忆: 把对话历史存在内存里, 每次请求时附带
- 长期记忆: 把用户偏好、历史任务存到向量库或关系数据库
- 用户画像: 抽取结构化的用户属性, 作为 system prompt 的一部分
- 知识图谱: 把实体和关系存起来, 跨会话维护



### 局限 5: 上下文窗口—工作记忆有上限

**表现**

LLM 一次能"看到"的文本长度是有限的:
- GPT-3.5: 4K tokens
- GPT-4: 8K → 32K → 128K
- Claude 3.5: 200K
- Gemini 1.5: 1M-2M

虽然窗口在变大, 但仍然有限。

**更糟的是**:

即使窗口变大, LLM 对长上下文的利用效率是非均匀的。学术上叫 **"Lost in the Middle"**——LLM 对开头和结尾的内容记得最清楚, 中间的内容容易被忽略。

```
[开头: 记得清]
   ...
   ... 中间内容  ← 容易"迷失"
   ...
[结尾: 记得清]
```

**为什么会这样?**

这是 Transformer 注意力机制的特性 + 训练数据偏短的共同结果。学术界还没有完美解决。

**严重性**

- 长文档分析: 超过窗口的文档截断后丢失信息
- 长对话: 超过几十轮后,早期对话被遗忘
- 多文档任务: 几十个文档塞进去,模型顾此失彼

**Agent 怎么解**

- RAG: 不把全部文档塞给 LLM,只检索最相关的片段
- 上下文压缩: 长对话定期摘要,只保留关键信息
- 滑动窗口: 始终保留最近 N 轮 + 关键早期轮次
- 分而治之: 长任务拆成多个子任务,每个子任务用单独的上下文



### 局限 6: 推理脆弱—复杂任务有时会想不通

**表现**

LLM 在简单任务上表现优秀, 但在需要多步推理的复杂任务上, 会"想歪"、"想浅"、"想错"。

```
User: 9.11 和 9.9 哪个大?
LLM: 9.11 更大(错误,9.9 更大)
```

这不是个例。LLM 在多步算术、复杂逻辑、嵌套推理上经常翻车, 即使是 GPT-4 级别。

**为什么会这样?**

LLM 的一次推理是单步的——它没有真正的反复思考机制,只是一个 token 接一个 token 预测。所谓"思考", 是涌现出的副产品, 不是设计好的能力。

**严重性**

- 数学计算: 不可靠
- 复杂业务逻辑: 不可靠
- 需要反事实推理的场景: 不可靠

**Agent 怎么解**

- CoT(Chain of Thought): 强制 LLM 一步步推理
- 工具调用计算: 让 LLM 把 "3.14 × 89" 交给计算器
- 多次采样 + 投票: 同一个问题问多次,选最一致答案
- Self-Critique: 让 LLM 审视自己的答案,发现错误就重做
- 任务分解: 把复杂任务拆成简单子任务,分别完成



### 局限 7: 不可解释——它不知道自己怎么"想"的

**表现**

你问 LLM:"你为什么这么回答?"
LLM 给你的解释**很可能不是它真实推理的过程**,而是一个"听起来合理"的解释。

**为什么会这样?**

LLM 的推理发生在数千亿参数的高维空间里。没有人能完整解释"为什么这次输出了 A 而不是 B"。即使是 LLM 自己, 也只能事后编造一个解释。

**严重性**

- 高风险场景(医疗诊断、法律建议): 无法审计
- 错误归因: 无法知道为什么这次错了
- 模型调试: 像在黑盒里调超参

**Agent 怎么解(部分)**

- Prompt 日志: 完整记录每次推理的输入输出
- CoT 显式化: 强制 LLM 把思考过程写出来 (虽然可能不真实, 但至少是"声称"的推理)
- 工具调用链: 每一步决策都对应可验证的工具调用
- 多模型辩论: 让两个 LLM 互相质疑,降低单模型的"伪解释"

> **说明**:这条局限 Agent 没有完全解开。这仍是 AI 领域的开放问题。


### 局限 8: 成本与延迟—它很贵, 而且不总是快

**表现**

一次 LLM 推理的成本:
- 小模型、简单任务: 0.001 美元 / 次
- 大模型、复杂任务: 0.1-1 美元 / 次
- 一次完整 Agent 任务(多步推理 + 工具调用): 可能 0.5-5 美元

延迟:
- 短回答: 0.5-3 秒
- 长生成: 10-60 秒
- 多步 Agent 任务: 30 秒到几分钟到几个小时

**严重性**

- To C 应用: 单次成本 0.01 美元,百万次就是 1 万美元
- 实时场景(客服、搜索): 3 秒延迟用户就开始不耐烦
- 高频任务(批量处理): 成本爆炸

**Agent 怎么解**

- 模型路由: 简单任务用小模型,复杂任务用大模型
- 缓存: 相似问题用缓存的答案
- 流式输出: 边生成边返回, 降低感知延迟
- 异步处理: 长任务放后台,完成后通知
- 提示词压缩: 缩短 prompt 减少 token



### 局限 9: 对齐与安全—它可能答非所问或答错所问

**表现**

LLM 可能:
- 被用户诱导输出有害内容
- 偏离系统设定的角色和行为规范
- 在多轮对话中"被带偏", 做出原始设定不允许的事
- 输出有偏见、歧视、违法的内容

**为什么会这样?**

LLM 是预测下一个 token, 不是严格遵守规则。任何对齐都是训练阶段灌输的偏好, 在推理时可以被绕过。

**严重性**

- 直接商业风险: 用户诱导后输出违法内容
- 品牌风险: Agent 说出不可控的话
- 法律风险: 某些行业有强制合规要求

**Agent 怎么解**

- 多层防线: 输入侧、推理侧、输出侧都加安全检查
- 工具调用权限边界: Agent 不能调任何工具,必须显式授权
- 沙箱执行: 工具执行的环境与生产隔离
- 红队测试: 主动找漏洞
- 输出审计: 记录所有输出,事后审查



## 2.2：Agent 是怎么解决这些局限

让我们把上面的九条局限和 Agent 的解法做个映射:

```
LLM 局限              →   Agent 解法              
─────────────────────────────────────────────────────────────
1. 幻觉                →   RAG / 工具验证 / 引用    
2. 知识截止            →   实时搜索 / 知识库外挂    
3. 无手无脚            →   工具调用 / Function Call 
4. 无状态              →   短期记忆 / 长期记忆      
5. 上下文窗口          →   RAG / 压缩 / 分而治之    
6. 推理脆弱            →   CoT / Self-Critique / 分解 
7. 不可解释            →   轨迹记录 / 显式推理      
8. 成本与延迟          →   模型路由 / 缓存 / 异步   
9. 对齐与安全          →   多层防线 / 沙箱 / 红队   
```

> 一个深刻的洞察: Agent 的全部架构设计, 本质上就是给 LLM "打补丁" 的过程。

每一条 LLM 的局限都对应一种或多种 Agent 机制。Agent 工程师的工作, 就是在这些机制之间做权衡、做组合、做取舍。

这意味着:

- 你不需要先理解 Agent 的全部最佳实践, 只需要先理解 LLM 的局限——然后每一种局限的解法, 自然就是 Agent 的一条设计原则。



## 2.3：原始 LLM vs Agent:一个对比表

最后, 让我们用一张表结束本节:

| 维度         | 原始 LLM(裸调用)     | Agent(包装后)                |
| ------------ | -------------------- | ---------------------------- |
| 能完成的任务 | 问答、写作、简单推理 | 真实业务任务、端到端流程     |
| 信息来源     | 训练数据             | 训练数据 + 实时搜索 + 知识库 |
| 操作能力     | 只能"说"             | 能"做"(调工具、执行代码)     |
| 记忆         | 一次会话             | 跨会话长期记忆               |
| 上下文       | 有限窗口             | RAG + 压缩 + 长期记忆        |
| 复杂任务     | 容易"想歪"           | 任务分解 + 自我反思          |
| 错误处理     | 输出错就错           | 验证 + 重试 + 兜底           |
| 成本         | 可控                 | 需要精细优化                 |
| 安全性       | 不可控               | 多层防御                     |
| 可观测性     | 黑盒                 | 完整轨迹                     |

Agent 不是 LLM 的替代品, 而是让 LLM 发挥全部能力的补充。

如果 LLM 是引擎, Agent 就是整车部件—加上传动、刹车、转向、车身, 才能上路。

**本节小结**:

> LLM 的九条局限, 定义了 Agent 工程的全部设计目标。一个合格的 Agent 架构师,必须把每条锁链对应的解法内化于心。
